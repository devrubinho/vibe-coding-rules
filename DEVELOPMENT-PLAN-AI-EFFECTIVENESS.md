# Development Plan — Maximizing AI Effectiveness (Claude-first)

> **Status:** ✅ Implemented (WU-01..15, all 15 done 2026-06-28) · **Owner:** Rubens · **Created:** 2026-06-28 · **Target package:** `rbin-task-flow`
>
> Goal: take RBIN Task Flow from "well-documented prose workflow the model must obey" to
> "deterministic guardrails + Claude-native parallelism", without breaking the existing
> Cursor/Codex parity. Each item below is independently shippable.

---

## 0. Guiding principles

1. **Mechanical work → CLI; judgment → LLM.** Anything that is pure rendering/validation
   should be a deterministic command, not regenerated by the model each turn. This saves
   tokens *and* removes a class of state-drift bugs.
2. **Policy → hooks, not only prose.** Rules the model "must" follow (e.g. no git-write)
   become deterministic when enforced by a hook. Keep the prose too (defense in depth).
3. **Claude can raise its own ceiling.** Subagents/parallelism are Claude-native; the
   copy-paste `split:N` model is the floor for Cursor/Codex, not the ceiling for Claude.
4. **Cross-platform parity is a constraint, not a goal per feature.** Claude-only features
   are fine *as long as* Cursor/Codex keep working with their current flow.
5. **Everything new must be wired for distribution** (see §7) — repo file, `package.json`
   `files[]`, `lib/install.js` copy + `dirs`, and the `reset --keep-tasks` upgrade path.

---

## 1. Architecture facts this plan depends on

| Fact | Source | Implication |
|------|--------|-------------|
| CLI commands registered via commander | `bin/cli.js` | New subcommands = new `program.command()` + a `lib/*.js` module |
| Templates copied verbatim into target | `lib/install.js` `copyConfigs()` | Shipping hooks/permissions = edit template `.claude/settings.json` |
| `dirs[]` whitelist creates target dirs | `lib/install.js` (~line 98) | New dir (`.claude/agents`) must be added here |
| `package.json` `files[]` is an allowlist | `package.json` | New shipped paths must be listed or they won't publish |
| `reset --keep-tasks` preserves task state only | `lib/install.js` `backupTaskFiles()` | New config files get refreshed on upgrade — intended |
| `.claude/settings.json` is currently `{}` | repo | Greenfield: no merge conflict risk for hooks/permissions |
| `status.json` is "source of truth", `tasks.status.md` is regenerated by the model | `task-flow-run/workflow.md` | Prime candidate for deterministic rendering (§3) |
| State files mutated by the model every run | skills | Need schema + validate for a self-check loop (§4) |

## 3. Phase 1 — Guardrails

### 1A. Git-write blocker hook (deterministic enforcement)

**Why.** `CLAUDE.md` and `AGENTS.md` say "never run `git add/commit/push/...`". Today that
is prose the model must remember. A `PreToolUse` hook makes it impossible regardless of
model behavior.

**Design.**
- Add `.claude/hooks/block-git-write.sh` (or `.js` for portability — Node is already a dep).
- Register in template `.claude/settings.json`:
  ```jsonc
  {
    "hooks": {
      "PreToolUse": [
        {
          "matcher": "Bash",
          "hooks": [{ "type": "command", "command": "node .claude/hooks/block-git-write.js" }]
        }
      ]
    }
  }
  ```
- The script reads the tool input from stdin, parses the `command`, and exits non-zero
  (blocking) when it matches `git (add|commit|push|pull|merge|checkout|reset|rebase)` —
  while allowing `git status|diff|log|show|branch`. Emit a clear message pointing to
  `/rbin-git`.
- Edge cases to handle: `git -C <path> commit`, env-prefixed (`FOO=bar git commit`),
  chained (`x && git commit`), aliases, and the `rtk git ...` proxy form from the user's
  global setup. Match on the presence of a git write verb anywhere in the command tokens,
  not just the first token.

**Files.** `.claude/hooks/block-git-write.js` (new), `.claude/settings.json` (edit),
`package.json` `files[]` (+`.claude/hooks/`), `lib/install.js` `dirs[]` (+`.claude/hooks`)
and copy step.

**Acceptance.**
- `git commit -m x` is blocked with a message; `git status` passes.
- Works after a fresh `init` and after `reset --keep-tasks`.
- Cursor/Codex unaffected (they ignore `.claude/`); their prose policy stays.

**Effort.** ~2–3h incl. edge-case tests. **Risk.** Low (greenfield settings).

---

### 1B. Permissions allowlist (fewer prompts)

**Why.** `settings.json` is empty, so every routine read-only command
(`head .task-flow/...`, `cat`, `git status/diff/log`, `graphify query`) can trigger a
permission prompt. The workflow runs these constantly.

**Design.** Add a conservative `permissions.allow` block to the template `.claude/settings.json`:
- Reads of `.task-flow/**`.
- `git status`, `git diff`, `git log`, `git show`, `git branch` (read-only git).
- `graphify query ...`.
- Do **not** allow anything that writes. Keep the list minimal and auditable.

**Files.** `.claude/settings.json` (edit only).

**Acceptance.** Fresh project: a normal `task-flow: run next` round trip triggers
noticeably fewer permission prompts; no write command is auto-allowed.

**Effort.** ~1h. **Risk.** Low. Pairs with `/fewer-permission-prompts` for tuning.

---

### 1C. Sync-reminder hook (state stays consistent)

**Why.** When the user edits `.task-flow/tasks.input.txt`, the system is out of sync until
someone remembers to run `sync`. A `PostToolUse` hook can surface a reminder deterministically.

**Design.**
- `PostToolUse` matcher on `Edit|Write` whose path is `tasks.input.txt`.
- Hook prints a non-blocking note: "tasks.input.txt changed — run `/task-flow-sync`."
- Keep it advisory (exit 0). Do **not** auto-run sync (sync needs model judgment to
  generate subtasks; auto-running would be surprising).

**Files.** `.claude/hooks/remind-sync.js` (new) + `.claude/settings.json` (edit).

**Acceptance.** Editing `tasks.input.txt` prints the reminder once; editing other files does not.

**Effort.** ~1–2h. **Risk.** Low. **Note.** Optional — lower value than 1A/1B; ship if cheap.

## 4. Phase 2 — Determinism

### 2A. JSON Schemas for `tasks.json` and `status.json`

**Why.** The model mutates these every run with no machine-checkable contract. A schema is
the foundation for both validation (2B) and safe parallel writes (Phase 3).

**Design.**
- Add `lib/schemas/tasks.schema.json` and `lib/schemas/status.schema.json` (JSON Schema draft 2020-12).
- Capture current shape: tasks with `id`, `title`, `originalRequest`, `subtasks[]` with
  `id`, `title`, `instructions`, `contexts?`; status with subtask state enum
  `pending | done | in_progress | manual` (matches `workflow.md`).
- Reverse-engineer exact fields from a real `.internal/tasks.json` / `status.json` before
  freezing the schema (do not guess field names).

**Files.** `lib/schemas/*.json` (new) + `package.json` `files[]` (+`lib/` already listed — confirm `lib/schemas` ships).

**Acceptance.** Current real state files validate against the schemas with zero edits.

**Effort.** ~3–4h (most of it is faithfully capturing the existing shape). **Risk.** Medium —
getting the schema wrong creates false validation failures. Mitigate by validating against
several real projects first.

---

### 2B. `rbin-task-flow validate --schema` (self-check loop)

**Why.** Gives Claude a deterministic way to confirm it didn't corrupt state after editing
JSON — instead of "trust that it's right".

**Design.**
- New command in `bin/cli.js` + `lib/validate.js`.
- Validates `.internal/tasks.json` and `status.json` against §2A schemas.
- Cross-checks referential integrity: every status entry maps to an existing task/subtask
  id and vice-versa (this catches the real-world drift bug, not just shape errors).
- Human-readable errors with the offending id/path; non-zero exit on failure (so hooks/CI
  can use it).
- Extend the existing `task-flow: validate` skill to call this CLI as step 0 before its
  deep codebase validation.

**Files.** `bin/cli.js` (edit), `lib/validate.js` (new), `.claude/skills/task-flow-validate/`
(reference the CLI), `.cursor/rules/task_validate.mdc` (parity).

**Acceptance.** Hand-corrupt a status id → command reports it with the id and exits non-zero;
clean state exits 0.

**Effort.** ~4–5h. **Risk.** Low once 2A is solid. **Depends on.** 2A.

---

### 2C. `rbin-task-flow render-status` (move rendering off the LLM)

**Why.** Today the model regenerates `tasks.status.md` from `status.json` on every run —
mechanical work that costs tokens and can drift. Make it a pure function.

**Design.**
- New command + `lib/render-status.js`: read `tasks.json` + `status.json`, emit the exact
  `tasks.status.md` format (checkboxes + 📊 Summary) the skills currently describe.
- Match the current markdown byte-for-byte where reasonable so diffs stay clean.
- Update `task-flow-run` / `task-flow-sync` skills + cursor rules: replace "regenerate the
  markdown" with "run `rbin-task-flow render-status`". The model still decides *status
  values* (judgment); the CLI only *renders* them (mechanical).

**Files.** `bin/cli.js` (edit), `lib/render-status.js` (new), all skills/rules that mention
regenerating `tasks.status.md`.

**Acceptance.** `render-status` on a real project reproduces the existing `tasks.status.md`;
running it twice is idempotent.

**Effort.** ~4–6h. **Risk.** Medium — must match existing format exactly to avoid noisy
diffs and confusion. **Depends on.** 2A (shape), uses status enum.

> **Token win note:** 2C is the single biggest per-run token saver in this plan — every
> `run`/`sync` currently re-emits the whole status markdown through the model.

## 5. Phase 3 — Claude-native parallelism

### 3A. Subagent definitions (`.claude/agents/`)

**Why.** Claude Code can run subagents in parallel, isolated contexts. The whole `split:N`
machinery already computes non-conflicting task groups — the missing piece is an executor.

**Design.**
- Add `.claude/agents/task-runner.md` — a subagent whose job is: "given a set of subtask
  ids, implement them following coding standards, update `status.json`, never git-write."
  Restrict its tool list (Read/Edit/Write/Bash/Grep; no Agent recursion by default).
- Optionally `.claude/agents/task-reviewer.md` for a verify pass.
- Each agent's prompt references the same standards (`coding_standards.mdc`) and the
  no-git-write policy (reinforced by the 1A hook anyway).

**Files.** `.claude/agents/*.md` (new), `package.json` `files[]` (+`.claude/agents/`),
`lib/install.js` `dirs[]` (+`.claude/agents`) + copy.

**Acceptance.** A fresh `init` produces working `.claude/agents/`; invoking the runner on a
single task completes it and updates status.

**Effort.** ~4–6h. **Risk.** Medium — concurrent subagents editing the repo can collide;
this is exactly what 3B's grouping must prevent.

---

### 3B. Rework `split` to dispatch subagents (Claude path)

**Why.** Turn `split:N` from "N copy-paste lines for N humans/IDEs" into "dispatch N
parallel subagents in one session" on Claude — while keeping the copy-paste output for
Cursor/Codex.

**Design.**
- Keep the existing non-conflict grouping logic (the hard part already works).
- Claude path: instead of emitting `task-flow: run a,b,c` lines, the skill spawns one
  `task-runner` subagent per non-conflicting group via the Task tool, then aggregates
  results and runs `render-status` (2C).
- Safety: groups must be file-disjoint (lean on graphify when present to confirm module
  boundaries); serialize anything touching shared files.
- After all subagents return, run `validate --schema` (2B) before reporting done.
- Cursor/Codex: unchanged — `task_split.mdc` still prints copy-paste lines.

**Files.** `.claude/skills/task-flow-split/` (Claude-native dispatch), keep
`.cursor/rules/task_split.mdc` as-is.

**Acceptance.** `split:2` on two non-conflicting tasks runs both via subagents in one
session, status correct, no merge collisions; Cursor still gets copy-paste output.

**Effort.** ~1–2 days. **Risk.** Medium-High (concurrency). **Depends on.** 3A; strongly
benefits from 2B + 2C.

## 6. Phase 4 — Robustness

### 4A. Unit tests for sync/diff + render

**Why.** `package.json` `test` is a stub; the sync diff (add/remove/modify, preserve status)
and the new `render-status`/`validate` are exactly the logic that breaks silently.

**Design.**
- Pick a light runner (node:test built-in — zero new deps, fits `engines >=14`... note: node
  built-in test runner needs >=18, so either bump `engines` or use a tiny dep like `uvu`).
- Cover: sync add/remove/modify with status preservation; schema validation pass/fail;
  render idempotency; referential-integrity check.
- Fixtures under `test/fixtures/`.

**Files.** `test/**` (new), `package.json` `scripts.test` + maybe `engines` bump.

**Acceptance.** `npm test` runs real assertions and passes; intentionally broken fixture fails.

**Effort.** ~1 day. **Risk.** Low.

---

### 4B. CI workflow

**Why.** No `.github/workflows/`. A published CLI that others install should gate merges on tests.

**Design.** `.github/workflows/ci.yml`: matrix on Node LTS versions, `npm ci`, `npm test`,
`npm run measure:rules`. Optionally run `validate --schema` against the repo's own `.task-flow`.

**Files.** `.github/workflows/ci.yml` (new).

**Acceptance.** PRs show a passing/failing check. **Effort.** ~2–3h. **Risk.** Low.

---

### 4C. Installer smoke test

**Why.** `lib/install.js` is the riskiest code (filesystem mutation, reset, keep-tasks). A
regression here breaks every consumer.

**Design.** Test that `init` into a temp dir produces expected files; `reset --keep-tasks`
preserves `tasks.input.txt` + `.internal/` + `dev-logs/` and refreshes configs (including
the new hooks/agents from Phases 1 & 3).

**Files.** `test/install.test.js` (new). **Acceptance.** Both paths verified in a temp dir.
**Effort.** ~4–6h. **Risk.** Low.

```
- Add .claude/agents task-runner (and reviewer) subagents (3A)

- Add unit tests for sync/diff, render, and validate (4A)
- Add GitHub Actions CI workflow (4B)
- Add installer smoke test for init and reset --keep-tasks (4C)
```

Then `/task-flow-sync` → `/task-flow-estimate all` → `/task-flow-split:N` (or, once 3B
lands, dispatch subagents for real).

can implement *and* self-verify it without holding the whole repo in context: closed scope,

> a shipped file. Never git-write — suggest a commit via `/rbin-git` at the end of each unit.
